## 实施顺序

### A. 修复可见性（ISSUE-UI-001）

分离最新生成结果预览与审批资格。最新 blocked 有图时展示诊断图、任务 ID、阶段及错误，无图时说明无可用预览。不得静默用旧 awaiting 图冒充本轮；允许明确选择历史图。blocked 保持不可批准、不可入正式候选，正常草稿整体确认保持不变。

### B. 先形成根因报告，再做针对性改动（ISSUE-PIPELINE-002）

只读比较 426、500、502、503 的：输入规格、模型/seed、实际正负提示词、姿态与投影、控制单元、各阶段输出及错误。定位每个偏差最早出现的阶段。报告必须区分代码缺陷、配置问题、模型视觉执行不确定性。不得把“没看手机”直接等同某参数错误。

重点审计：
1. 身份：基础身份控制是否发送；串行身份仅 face mask 时，长发/发色/服装分别由谁建立，coverage 声明是否超出真实能力。gaze 中计划身份控制与实际发送是否一致，缺失是否有原因。不能以扩大脸部 mask 自动解决全部身份问题。
2. 交互：人物、手数、主动手、动作目的、对象实例、接触点、目标表面、视线是否贯穿 prompt/pose/guide/payload/pass；不是只查字段存在。
3. 几何：完整骨架到选定构图只有一个投影，局部 crop/mask/guide 的坐标一致；计划坐标不得冒充图像检测坐标。镜头可灵活，但各层不能采用相反景别。
4. 检测：检查手部检测的实际输入裁剪、分辨率、锚点覆盖、返回结构及可用性判定。区分调用失败、空响应、几何越界、检测未命中和正常遮挡，禁止靠降低阈值掩盖问题。
5. 后处理：每个 pass 的允许修改区、依赖与保护内容明确；对象-only 不能宣称修复整个手物关系。需要全局重建时提供有依据的重试策略；没有视觉检测器时不能自动断言结构合格或错位。

已确认且与旧根因一致的缺陷，补证据后复用旧 ISSUE；独立根因建唯一 open ISSUE。只有风险则记录未验证假设。不要为了让队列有任务而编造缺陷。

### C. 项目级决策统一

优先复用既有结构化契约与共享几何，不另造并行体系。分清剧情必须事实、身份服装连续性与未锁定构图偏好。携带/阅读/通话/交接分别处理，不从道具名称自动推出动作。单/双手与对象形状由关系驱动，不硬编码角色、job ID 或手机坐标。

控制预算按必要关系仲裁；不足则明确阻断或可证明等价的执行策略，不再静默遗漏。不要无评估地继续增加 CPU 控制数。局部处理按能力与需要启用，不能默认更多 pass 效果更好。不先换模型、不一键回退历史配置。
